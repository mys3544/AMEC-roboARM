02  Where we stand

Both software blockers are cleared, the preflight passes end to end from inside a container, and the hardware fault it appeared to find turned out not to exist. Nothing now blocks phase 2.

Resolved — the arm is fine, and the SDK was lying to us

The first preflight showed J3 reading -1 on every individual query and -57 in the batch call, which reads exactly like a dead elbow servo. It was not. Releasing torque and moving the arm by hand brought J3 back immediately, reporting a clean 95° sweep, and all six servos now reply.

The cause is a trap in the SDK worth knowing about permanently: get_uart_servo_angle() returns -1 for both a servo that never replied and a servo that replied normally while sitting outside its valid range. It clamps with if angle > 180 or angle < 0: angle = -1, and only reaches that line after the servo has answered. The arm had been resting below J3's zero position. A working servo came close to being replaced.

The fix, now in the preflight: liveness is tested with get_uart_servo_value(), whose returned read_id matching the address proves the servo answered regardless of where it is sitting. The angle is read separately, and "replied but angle is -1" is reported as out of range, not as a fault. Reads are also retried, because each call is its own bus transaction and single reads are occasionally missed — which produced a second false positive on J4 before it was fixed.

Cleared — the factory app no longer owns the hardware

Yahboom's rosmaster_main.py was holding both /dev/ttyUSB0 and /dev/video2, which is why the arm SDK reported every servo as -1 and the battery as 0.0 V. Stopped, and the autostart entry renamed to start_app.sh.desktop.disabled-by-roboarm. Restoring the factory web UI is one mv away. With it gone, the battery reads 12.0 V and the Orbbec RGB camera streams 1280×720 at ~10 fps.

Cleared — the broken login environment no longer matters

~/.bashrc is still a stale ROS 1 Melodic leftover that leaves ROS_DISTRO empty and ros2 off PATH. We no longer care, and we have not touched it: our code runs inside its own container with its own Python, so whatever other teams have done to the host environment cannot reach us. That is what section 03 is about.

Still worth knowing

The robot is on WiFi only (wlP1p1s0), and the host sets ROS_DOMAIN_ID=6 — if another machine in the lab shares that domain, topics will cross. We pick a private domain ID if and when we add ROS nodes.

03  Staying out of everyone else's way

Five teams have left state in /home/jetson. The host Python already has a source-built OpenCV shadowing two pip wheels of a different version. We isolate completely — uv for reproducible Python, Compose for everything else.

The split is deliberate: two services, and the one that matters most has no CUDA in it at all. Days 1–3 need serial, ArUco and geometry — nothing that requires a GPU. Making the demo-safe path depend on a multi-gigabyte CUDA image would put the whole demonstration behind the most fragile part of the stack.

ServiceBaseSizeHoldsWhen
core python:3.10-slim + uv 801 MB Arm, cameras, ArUco, geometry, teleop Always
vision dustynv/l4t-pytorch:r36.4.0 ~10 GB YOLO26 / YOLOE-26 behind an HTTP endpoint --profile vision, day 4

The vision service holds no camera. Core grabs the frames and posts them across, which avoids V4L2 contention between containers and means the detector ladder from section 05 degrades on its own: if the vision container is not running, core simply falls back to ArUco.

Four mechanics I checked rather than assumed

QuestionAnswer
How does a container get CUDA on JetPack 6? Not the legacy CSV path — this toolkit (1.18) uses CDI. Neither --runtime nvidia nor the NVIDIA_* env vars inject anything; devices: [nvidia.com/gpu=all] does, and puts libcuda.so.1 in place. Tested
Can devices be passed by stable name? Yes — Compose resolves /dev/serial/by-id/… and /dev/v4l/by-id/… symlinks and remaps them to fixed names inside the container. USB re-enumeration on the host can no longer shuffle which camera is which. Tested
Is the arm SDK installable? No — Rosmaster_Lib is not on PyPI. It is a single 1331-line pure-Python file in a zipped egg, needing only pyserial. tools/vendor_sdk.sh extracts it from the robot's own install, so the vendored copy always matches this hardware. We wrap it; we do not edit it. Working
Does upgrading Ultralytics break CUDA torch? Not in the core image, which has no torch at all. In the vision image we install with --no-deps into the base image's existing Python, and the build fails rather than the demo if torch.cuda.is_available() stops being true. Guarded
What this buys us

Nothing we do can break another team's project, and nothing they do can break ours. The full list of what we changed on the host is: installed uv into ~/.local/bin, created ~/roboarm, stopped the factory app, and renamed one autostart file. No shared config edited, no system package installed, no .bashrc touched.

04  The arm, and why we do not need MoveIt

MoveIt is not installed. It also is not needed: a previous team left a URDF with the full arm chain, and the geometry it describes has a closed-form solution.

The chain is base yaw, then three pitch joints that all rotate in the same plane, then a wrist roll. That is the textbook planar 3R on a turntable — it inverts analytically in about eighty lines of Python we can read in one sitting, with no solver, no planning scene, and no dependency to keep alive.

The constraint this puts on us

Five degrees of freedom means the tool's yaw is tied to the base yaw — the arm cannot reach an arbitrary 6D pose. Top-down and angled grasps are fine; side grasps at an arbitrary heading are not. Every demo below is designed around top-down picking, which is also the most reliable kind.

Second constraint: ±1–2° of servo readback error at ~250 mm reach is roughly 4–9 mm at the fingertip, and the gripper has no force feedback. We pick objects that are forgiving — graspable in a 25–45 mm window, slightly compliant, not fragile.

The single biggest unknown

That URDF came from a previous team's folder and has never been checked against this physical robot, and nothing anywhere maps servo angle (0–180°, the units the SDK speaks) onto URDF joint angle (radians, signed, with offsets). Getting that mapping wrong is the classic way to lose two days. Phase 2 exists to nail it down and measure the residual error, before anything depends on it.

05  Detection: a ladder, not a bet

You flagged object detection as the thing you are least sure of. The fix is not to pick the best detector — it is to make the detector swappable, so the demo can never hard-fail on it.

Everything downstream consumes one small structure: a label, a pixel position, and a confidence. Four detectors implement it. We build the ladder bottom-up, and at every point in the week there is a rung that is known to work.

TIER 0Day 3

ArUco markers Guaranteed

A marker on each object. Deterministic, lighting-insensitive, gives full 6D pose, already verified working on this machine. This is the rung we demo from if anything else misbehaves on the day.

TIER 1Day 3

Colour + shape

HSV segmentation for objects that are distinct by colour. Thirty lines, no model, no GPU. Useful as a sanity check that the whole pick pipeline works before neural detection enters the picture.

TIER 2Day 4

YOLO26 Primary

Released January 2026 and genuinely a better fit for us than YOLO11: it is NMS-free and end-to-end, so there is no NMS threshold to tune and latency is predictable — both of which matter more on a demo floor than a point of mAP. yolo26n is 40.9 mAP at 1.7 ms on a T4; the Orin will be comfortably real-time. Fine-tuned on our actual objects it becomes very hard to break.

TIER 3Day 5

YOLOE-26 open-vocabulary

Text-prompted detection and segmentation with no retraining — this is what makes "say any object name and the arm picks it" real rather than a fixed class list. Strongest story, loosest guarantees, so it sits on top of a stack that already works without it.

One upgrade, handled carefully

YOLO26 needs Ultralytics ≥ 8.4; the robot has 8.3.65. I checked the dependency metadata: core Ultralytics only requires torch>=1.8, so the NVIDIA CUDA build of PyTorch 2.5 survives the upgrade — the torch>=2.12 pins people worry about apply only to the export extras, which we do not install. We still do it inside a virtualenv with --system-site-packages so the system Python stays exactly as other people on this robot left it.

06  One core, two demos

Both demos you picked share the same foundation. Building that foundation once, well, is what makes the second demo cost a day instead of a week — and what makes everything after this week cheap.

And immediately, a lesson

Look at J3=-57 — a number that sailed through a check written to catch exactly this. The tool trusted the batch readback, which reports a garbage byte rather than an error for a servo that never answered. The preflight now cross-checks every joint with an individual read, because a health check that reports a dead joint as a plausible number is worse than no health check at all.

The one design decision worth arguing about

I want to make table-plane homography the primary way we locate objects, and treat depth as an enhancement rather than a dependency.

We are picking objects off a flat table with a camera bolted to the robot. Under those conditions, four ArUco corners define a plane, and a single 3×3 homography maps any image pixel straight to table coordinates — about twenty lines, sub-centimetre, and completely immune to the depth-sensor problems that eat demo days (specular objects, IR interference, dropouts at close range, a driver we have not yet been able to test because the factory app was holding the camera).

Depth then earns its place where it genuinely adds something — object height for stacking, obstacle awareness, bin-picking later — instead of being a single point of failure under the entire demo. If the Orbbec depth stream turns out to work perfectly on day one, we lose nothing by having built this way.

07  The week

Seven working days. Each phase ends in a gate that is measured, not eyeballed — if a gate does not pass, we do not start the next phase, because everything downstream inherits the error.

01
Day 1 · mostly done

Take control, and make the arm safe to be wrong

Done Factory app stopped and autostart disabled. Isolated core container building in about thirty seconds. SDK vendored. config.py and check_hardware.py written, and the preflight passes 8/8 against real hardware — which is how we found the elbow fault on day zero instead of day two.

Done arm.py is the only module allowed to command the servos. It refuses to start on a silent board, a flat battery, or any joint outside its range; asserts the SDK's command gate rather than assuming it; interpolates every move so no step exceeds 8°; verifies arrival by readback; and leaves the arm holding, never limp, on exit. Backed by 17 tests that need no hardware.

Gate — passed Preflight 9/9. Ten home/start round trips, every commanded angle confirmed by readback, worst-case spread 1° — about 4–5 mm at the fingertip, so the 10 mm target in phase 2 is reachable.
02
Day 2

Kinematics, and proving the URDF is true

Measure the physical arm and check it against the URDF. Pin down the servo-angle to joint-angle mapping empirically: command each joint to known values, read it back, photograph the pose, and fit the sign and offset. Write FK and the closed-form IK, with unit tests that round-trip random poses through IK and FK on a laptop — no hardware, no robot time.

Gate IK/FK round-trip error under 1 mm in software. On the robot, commanding ten known Cartesian points puts the fingertip within 10 mm of each, measured against a printed grid.
03
Day 3

Teaching the camera where the table is

Print an ArUco board, fix it to the table, and solve the homography from camera pixels to table coordinates. Cross-check it with hand-eye calibration using a marker on the gripper and cv2.calibrateHandEye. Then close the loop: the robot touches a point you indicate on a live camera image. Build the pick, place and home primitives on top.

Gate Click any point on the table in the camera view and the fingertip lands within 10 mm of it. A cube with an ArUco marker is picked and dropped in a bin 9 times out of 10. Demo-safe from here on
04
Day 4

Demo A — name it, and the arm picks it up

Upgrade Ultralytics inside a venv, pull yolo26n, and drop it behind the detector interface built on day 3 — the pick pipeline does not change, only where the pixel comes from. Fine-tune on a few hundred images of our actual demo objects, which is an afternoon on this Orin and buys a large amount of reliability. Export to TensorRT.

Gate Five different objects, ten attempts each, picked and placed at 8/10 or better per object, with the ArUco path still working as a fallback on the same code.
05
Day 5

Demo B — show it once, it repeats

This is where the arm's torque-disable and position readback pay off. Cut torque, guide the arm through a task by hand while recording joint angles at 20 Hz, then replay it through the same safety layer. The important part is the next step: record the trajectory relative to a detected object, so replay follows the object when you move it, instead of blindly repeating fixed angles.

Gate A demonstrated pick-and-place replays 5 out of 5 from three object positions the demonstration never visited.
06
Day 6

Manual driving, and one screen to run it all

Gamepad or keyboard teleop for the mecanum base so you can reposition the robot between runs, with the arm forced to a safe stowed pose whenever the wheels are live. A single operator view: camera feed with detections drawn, current joint angles, battery, and the active demo mode. Add open-vocabulary YOLOE-26 as a selectable rung now that everything beneath it is solid.

Gate Drive the robot to a new table position, re-run the table calibration in under two minutes, and pick successfully from the new position.
07
Day 7

Break it on purpose, then rehearse

Deliberate failure injection: cover the camera, move an object mid-grasp, yank the object out of the gripper, pull the serial cable. Each one should produce a clear message and a safe state, never a thrown exception with the arm mid-air. Then run the demo end to end five times in the actual room, with the actual lighting, on battery.

Gate Five consecutive clean runs. A written one-page run sheet, including what to say while the arm is moving and which rung to drop to if detection misbehaves in the room.
If the week compresses

The demo is safe from the end of day 3 — ArUco picking is a complete, honest demonstration of vision-guided manipulation. Days 4–7 raise the ceiling. Protect days 1–3 at all costs; everything after them is negotiable.

08  Risk register

The things most likely to cost us a day, and what we do about each.

RiskImpactMitigation
Trusting a single SDK read Medium Already bit us twice in one session — once reporting a healthy servo as dead, once flagging an in-range joint as out of range. Every read is retried, liveness and position are asked as separate questions, and no diagnosis is made from one sample.
Servo ↔ URDF angle mapping is wrong High Phase 2 exists solely to establish it empirically and measure the residual. Nothing downstream starts until the 10 mm gate passes.
Orbbec depth driver does not come up Medium Already designed around: homography is the primary path, depth is an enhancement. Costs us stacking, not the demo.
Detection unreliable in demo lighting Medium The four-rung ladder, plus a rehearsal in the actual room on day 7. Fine-tuning on our own objects is the single biggest win here.
Gripper drops or crushes objects Medium No force feedback exists on this arm. We choose compliant objects in a 25–45 mm grasp window and verify grip by readback — if the gripper closes further than expected, the object is not there.
Ultralytics upgrade breaks CUDA PyTorch Low Dependency metadata already checked — core needs only torch>=1.8. Done in a venv regardless, so the system Python is untouched.
WiFi drops mid-demo Medium Everything runs on the robot. The laptop is a viewer, not a participant — pulling the network mid-demo must not stop the arm.
Someone else uses the robot mid-week Low We change no shared config. Our environment is one file, our code is one folder, and the factory app restore is one command.
Battery sags under arm load Medium Voltage logged in the operator view from day 1, so we learn the real endurance early rather than discovering it during the demo.

09  After the demo

The core built this week is deliberately the substrate these need. Roughly in order of value-for-effort, not difficulty.

Weeks 2–4 — learned manipulation

Day 5 gives us demonstration recording; the natural next step is to stop replaying trajectories and start learning policies from them. LeRobot is the obvious vehicle — an arm with torque-disable and position readback is exactly the hardware its recording pipeline expects, and ACT or a diffusion policy trained on a few dozen demonstrations generalises where a replay cannot. Everything trains and runs on this Orin.

Weeks 4–8 — language over the top

A vision-language model turning "clear the table" into a sequence of the picks we already have. The groundwork is on the machine already — SmolVLM in quantised ONNX and Moondream both sit in ~/visionLanguageModels, and there is a USB microphone for spoken commands. The interesting question is not whether the VLM can plan, it is how the plan is verified before a real arm executes it.

Weeks 8+ — the whole robot

Nav2 and the RPLidar are installed and untouched by this plan. Mobile manipulation — drive somewhere, pick something, bring it back — is the demo that uses the entire machine, and it is a great deal easier once picking is a solved, measured primitive rather than the thing being debugged.

The honest research direction

Vision-language-action models are where this field is, and this Orin NX can run the small ones. That is a genuine research project rather than a demo, and it wants the data infrastructure from weeks 2–4 to exist first. Worth planning toward; not worth starting from.

Next at the robot: the arm is currently limp — torque is still off from the diagnostic. Re-engage with docker compose run --rm core python tools/arm_release.py --engage, holding the arm while it re-stiffens.

Still open: which objects should the demo pick (I would like five that are 25–45 mm across and slightly compliant); is the robot on a fixed table or does it move between rooms; and is there a wired network option in the demo room, or are we on WiFi.

Every hardware claim on this page was verified over SSH on 1 September 2026 and re-confirmed from inside the core container. The one thing still untested is the Orbbec depth stream — its RGB stream works, and the plan deliberately does not depend on depth.

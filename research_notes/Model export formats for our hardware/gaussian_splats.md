# Gaussian splats: fastest training, export and rendering formats for our hardware (state on 2026-10-27)

Context, read from the repo (not from the web): `train/splat/train_splat.py` fits with gsplat 1.5.x (`rasterization(..., packed=False, render_mode="RGB+ED")`, `DefaultStrategy`, a hand-written Python SSIM, plain `torch.optim.Adam` per parameter group, SH degree ramped 0 -> 3 by step 3000, a 6D pose correction per view, 7000 steps, up to 150k starting points), writes the standard PLY and an antimatter15 `.splat` that keeps only DC colour (shN dropped) and Gaussians with opacity >= 2 % inside the scan's reach. `console/cloud.js` parses the `.splat` on the main thread into an RGBA32F texture of 4 texels (64 bytes) per Gaussian, sorts on the main thread with a 16-bit counting sort whenever the view changes, and draws instanced quads (EWA projection, +0.3 px blur, 3-sigma cut-off, premultiplied back-to-front blending), no SH.

## 1. Training speed: gsplat now, other fast trainers, and what a ~1 minute fit from 20-60 RGB-D views can be

### Takeaway
The newest gsplat on PyPI is still 1.5.3 (4 Jul 2025), but gsplat's main branch has had a stream of 2026 speed work (faster 3DGS/3DGUT kernels, AccuTile intersection, sparse active-tile rasterization, fused SE(3), CUDA 13.2) that is not yet in a PyPI release. For a small object scan the biggest wins on our side are in our own loop (fused SSIM, a sparse/fused Adam, an MCMC budget, no SH work the viewer throws away), not in switching trainers; the 2025-2026 "fast" papers (FastGS ~100 s, the 1-minute SIGGRAPH Asia challenge winner, Faster-GS 4.1x) target full scenes and mostly build on the original 3DGS/Taming codebases rather than gsplat.

### Cited Findings
- gsplat PyPI history: latest release 1.5.3 (Jul 4, 2025); before it 1.5.2 (May 13, 2025), 1.5.1 (Apr 18, 2025), 1.5.0 (Apr 4, 2025), 1.4.0 (Sep 27, 2024). No 2026 release listed. — [PyPI gsplat](https://pypi.org/project/gsplat/#history)
- gsplat 1.5.0 (Apr 2025): ~3.5x faster compilation (4m19s -> 1m22s), up to 25 % faster `rasterization` from a tighter Gaussian-tile intersection, `SelectiveAdam` (fused CUDA Adam with a mask), densification moved after the optimizer step. 1.5.1: `export_splats` exporter API for `.ply`, `.splat` and `.ply_compressed` (SuperSplat's compressed PLY), faster fused-SSIM. 1.5.2: 3DGUT integrated (distorted cameras, rolling shutter), 2DGS pose gradients, bundled nerfstudio-style viewer. 1.5.3: batched rendering of several scenes in one call, F-Theta camera, Windows CI (Windows Server 2022). MCMC and absgrad date from v1.1.0 (Jul 2024), multi-GPU from v1.2.0. — [gsplat releases](https://github.com/nerfstudio-project/gsplat/releases)
- gsplat main, after v1.5.3 and unreleased on PyPI (README news list): Jan 2026 PPISP (alternative to bilateral grids for per-view appearance); Mar 2026 LiDAR rasterization, TorchScript custom-op deployment, 3DGUT extensions; Apr 2026 AccuTile ellipse-based tile intersection, NCore v4; May 2026 native CUDA MCMC `inject_noise`, experimental inference rendering (HiGS); Jun 2026 faster 3DGS/3DGUT rasterization ("roughly 30% improvement on the 3DGUT MCMC path on an NVIDIA A100"), Gaussian-ID rasterization (IDs/counts/top contributors per pixel), fp16 and arbitrary-channel SH, CUDA 13 + NumPy 2, simplified namespace; Jul 2026 faster 3DGS/3DGUT kernels, fused SE(3) ops, configurable MCMC relocation, multi-GPU for the dense path, sparse active-tile rasterization, and "PyTorch 2.7+ is now required, with CUDA 12.8 and 13.2 build compatibility"; Aug 2026 split/fused SH kernels with optimised backward. README claims up to 4x less GPU memory and up to 15 % less time than the official 3DGS implementation, and prebuilt Linux and Windows wheels for some Python/PyTorch/CUDA combinations. — [gsplat README](https://github.com/nerfstudio-project/gsplat)
- NVIDIA 3DGRUT (3DGRT ray tracing + 3DGUT unscented-transform rasterization): v1.0.0 Apr 2025 (MCMC, SparseAdam, masks), Windows + multi-sensor Jul 2025, PPISP Jan 2026, NCore v4 Mar 2026, v2.0.0 Jun 2026 (Neural Harmonic Textures). Own tables on an RTX 5090: 3DGUT on MipNeRF360 ~686 s training at 317 FPS; 3DGRT ~2,869 s at 68 FPS; NeRF-Synthetic 3DGUT ~215 s / 846 FPS. CUDA 11.8-12.8 (12.8 default, Blackwell via 12.8), 13.0 experimental; Linux and Windows. — [nv-tlabs/3dgrut](https://github.com/nv-tlabs/3dgrut)
- FastGS ("Training 3D Gaussian Splatting in 100 Seconds", arXiv 2511.04283, v3 6 Dec 2025, CVPR 2026 poster): 3.32x faster than DashGaussian on Mip-NeRF 360 at comparable quality, 15.45x faster than vanilla 3DGS on Deep Blending; GPU and base code not stated on the abstract page; project page fastgs.github.io. — [arXiv 2511.04283](https://arxiv.org/abs/2511.04283); [CVPR 2026 poster](https://cvpr.thecvf.com/virtual/2026/poster/39191)
- FastGS's own same-protocol table (as quoted in search snippets, units presumably minutes): Deep Blending playroom Taming-3DGS 3.35, DashGaussian 4.70, Speedy-Splat 9.70, 3DGS 16.75, FastGS 1.22; T&T truck 2.38 / 4.25 / 7.22 / 12.50 / 1.30. — [FastGS PDF](https://arxiv.org/pdf/2511.04283)
- "Fast Converging 3DGS for 1-Minute Reconstruction" (arXiv 2601.19489, 27-28 Jan 2026): won the SIGGRAPH Asia 2025 3DGS Fast Reconstruction Challenge (PSNR 28.43) under a strict one-minute budget; round 1 (noisy SLAM poses) builds on Taming-GS and Speedy-Splat with per-Gaussian parallel backward, load-balanced tiling, anchor-based Neural Gaussians, monocular-depth/feed-forward initialisation and global pose refinement; round 2 (COLMAP poses) drops pose refinement and Neural Gaussians, adds multi-view-consistency splitting (from FastGS) and depth supervision. Faster-GS (CVPR 2026): 4.1x faster than 3DGS with 30 % less VRAM on Mip-NeRF 360, RTX 4090. Speedy-Splat: training only ~1.38x faster (its target is render speed/size via pruning). DashGaussian: ~45.7 % average speed-up as a scheduler over several backbones. — [arXiv 2603.09277](https://arxiv.org/pdf/2603.09277); [Faster-GS CVPR 2026](https://openaccess.thecvf.com/content/CVPR2026/papers/Hahlbohm_Faster-GS_Analyzing_and_Improving_Gaussian_Splatting_Optimization_CVPR_2026_paper.pdf); [Speedy-Splat](https://arxiv.org/html/2412.00578v2)
- Brush (Rust + Burn, WebGPU): runs on Windows/macOS/Linux, AMD/NVIDIA/Intel, Android and Chrome 134+; reads COLMAP and nerfstudio datasets with masks; loads `.ply` / `.compressed.ply`; README says training and rendering are "generally faster than gsplat" (no numbers); depth input not mentioned. — [Brush](https://github.com/ArthurBrussee/brush)
- Feed-forward (no per-scene optimisation): DepthSplat reported ~0.6 s for 12 views at 512x960; YoNoSplat 100 views at 280x518 in 2.69 s on a GH200, posed or pose-free; AnySplat predicts Gaussians and cameras from unposed images; ReCoSplat (2026) takes posed or unposed input with a render-and-compare module; 2Xplat (2026) separates geometry and appearance. (Numbers from search-result summaries, not re-read in the papers.) — [DepthSplat](https://lamarr-institute.org/publication/depthsplat-connecting-gaussian-splatting-and-depth/); [YoNoSplat PDF](https://arxiv.org/pdf/2510.08575v1); [AnySplat](https://papers.cool/arxiv/2505.23716); [ReCoSplat](https://papers.cool/arxiv/2603.09968); [2Xplat](https://arxiv.org/pdf/2603.21064)

### Inferences
- Our ~1 min for 7000 steps on an RTX 5090 is slow for an object scan at RGB-D resolution with <= ~300k Gaussians; per-step Python overhead (hand-written SSIM with conv2d, six separate Adam optimizers, depth loss, pose net) is likely a large share. Cheap, low-risk changes inside `train_splat.py`: use `fused_ssim` (the CUDA SSIM gsplat's own trainer uses); one `SelectiveAdam`/SparseAdam for the Gaussian params (gsplat 1.5.0); `packed=True` and `absgrad=True` (with the absgrad grow threshold, ~2x the default, as gsplat's examples do); or `MCMCStrategy(cap_max=...)` to fix the Gaussian budget (predictable file size, no densify spikes). Since the console drops shN, train with `sh_degree` 0-1 for console-only splats and keep degree 3 only if the PLY goes to Isaac Sim / SuperSplat.
- Moving from gsplat 1.5.3 to gsplat main gets the 2026 kernels but requires PyTorch >= 2.7 and may change the Windows JIT build that our `build_gsplat_for_msvc()` workaround patches (the -Wno-attributes issue was seen on 1.5.3); test in a separate venv on hekate first.
- FastGS / Taming / the 1-minute challenge code target ~30k-step scene-scale fits on COLMAP data; their tricks (multi-view-consistent splitting, load-balanced tiling, per-Gaussian backward) matter less for a 20-60 view object at 640x480. Realistic target with gsplat and our RGB-D supervision: a few thousand steps in ~20-40 s on the 5090 at the same held-out PSNR, but this must be measured (section 6).
- Feed-forward models build splats in ~1-3 s but are trained on room/scene datasets and generally score below per-scene optimisation; useful as an initialiser (as the challenge winner did) or as a live preview on the robot, not as the final asset. Our RGB-D back-projection already gives a good initialisation, so the gain is smaller for us than for RGB-only pipelines.
- Brush is the only trainer that would run in a browser or on Android/Jetson-class GPUs via WebGPU, but without depth supervision and pose refinement it would likely be worse on our scans than our gsplat loop.

### Gaps
- No gsplat PyPI release after 1.5.3 found; whether the July 2026 Windows/CUDA 12.8 build still needs our MSVC workaround is unknown.
- No same-hardware benchmark of gsplat vs 3DGRUT/3DGUT vs Brush vs FastGS on small object scans with depth; 3DGS-LM (Levenberg-Marquardt) numbers were not found in the snippets.
- No feed-forward model found that takes posed RGB-D (metric depth) as input specifically; DepthSplat's input modality not confirmed.

## 2. File formats and compression: PLY, .splat, .ksplat, SPZ, SOG, compressed PLY, glTF KHR_gaussian_splatting, OpenUSD

### Takeaway
For delivery: SOG (PlayCanvas, ~15-20x smaller than PLY, lossless-WebP images of quantised attributes) and SPZ v4 (Niantic, ~10x smaller, ZSTD streams) are the two compact formats with the widest reader support in 2026; both are produced by PlayCanvas's `splat-transform` CLI from our PLY. For interchange: glTF `KHR_gaussian_splatting` was ratified (registry commit dated 2026-09-03, no press release) with compression left to separate draft extensions (SPZ-based), and OpenUSD 26.03 (Mar 2026) added `UsdVolParticleField3DGaussianSplat`, which is what Omniverse RTX / Isaac Sim 6 render natively.

### Cited Findings
- SPZ (Niantic): current version 4 = ZSTD per attribute stream, 32-byte header, magic "NGSP"; v1-v3 legacy gzip, read-only. Quantisation: positions 24-bit fixed point; scales 8-bit log per axis; rotation smallest-three at 10 bits + 2-bit index; alpha and colour 8-bit; SH 8-bit with configurable packing (`sh1Bits` default 5, `shRestBits` default 4). "Typically around 10x smaller than the corresponding .ply". Default coordinate system RUB (OpenGL/three.js); PLY usually RDF, GLB LUF; `SPZ_ADOBE_coordinate_system` extension. Python bindings via nanobind (`pip install .` from a clone, no PyPI package mentioned). Raw field widths ~20 B/Gaussian before SH (+9/24/45 B for SH1/2/3) before ZSTD (arithmetic from the field list). — [nianticlabs/spz](https://github.com/nianticlabs/spz)
- SOG v2 (PlayCanvas): a set of lossless WebP images + `meta.json`, or one `.sog` ZIP; positions 16 bit/axis (two 8-bit images, log-domain ranges), rotation smallest-three 26 bits, scale and DC colour as 8-bit indices into 256-entry codebooks, opacity 8 bit, higher SH as a palette (up to 65,536 entries, 1-3 bands) plus a 16-bit label per Gaussian; `model` field may be "antialiased" or "2dgs"; right-handed, y-up; lossy WebP must not be used. Fixed fields ~17 B/Gaussian (19 with SH labels) before WebP compression (arithmetic from the spec). — [SOG spec](https://developer.playcanvas.com/user-manual/gaussian-splatting/formats/sog/)
- PlayCanvas example: a 4M-Gaussian scene, 1 GB PLY -> 42 MB SOG (~95 % smaller); streamed SOG with LOD chunks for >= 1M Gaussians in SuperSplat. — [PlayCanvas blog](https://blog.playcanvas.com/playcanvas-open-sources-sog-format-for-gaussian-splatting/); [SuperSplat streaming](https://developer.playcanvas.com/user-manual/supersplat/streaming/)
- PlayCanvas engine formats: PLY (lossless, training/editing), SOG (~15-20x smaller, "optimized for web delivery"), streamed SOG (tens of millions of Gaussians), GLB with KHR_gaussian_splatting (lossless, PLY-sized), SPZ (~10x smaller, via a parser script). — [PlayCanvas formats](https://developer.playcanvas.com/user-manual/gaussian-splatting/formats/)
- `splat-transform` (`npm install -g @playcanvas/splat-transform`): reads PLY, compressed PLY, SOG, streamed SOG, SPZ, LCC, KSPLAT, SPLAT; writes PLY, compressed PLY, SOG, streamed SOG, SPZ (`--spz-version 3|4`, default 4), GLB (KHR_gaussian_splatting), CSV, single-file HTML viewer, voxel `.voxel.json` (with a `--collision-mesh` option), WebP renders. Filters: `-H/--filter-harmonics n` (drop SH bands above n), `-N` NaN, `-V opacity,gt,0.5`, box/sphere/floater/cluster filters, `--decimate` / `--decimate-adaptive`, `-m` Morton order; `-g <n|cpu>` GPU for SOG compression, `-i/--sh-iterations` (default 10). Example: `splat-transform input.ply output.sog`. — [splat-transform](https://github.com/playcanvas/splat-transform)
- Spark 2.0's own size figures: PLY ~230 B/splat (2.3 GB per 10M), SPZ ~20-25 B/splat (200-250 MB per 10M); new streamable `.RAD` (64K-splat chunks, JSON header, per-property gzip) built by a `build-lod` CLI; Bhatt-LoD trees ~30-40 % larger than input. — [World Labs, Spark 2.0](https://www.worldlabs.ai/blog/spark-2.0)
- glTF `KHR_gaussian_splatting`: README status "Complete, Ratified by the Khronos Group"; attributes POSITION, ROTATION (float/snorm8/snorm16), SCALE (float/unorm8/16), OPACITY (float/unorm8/16), SH degree 0 required, 1-3 optional (no partial degrees, 45 coefficients total), kernel "ellipse", colour spaces `srgb_rec709_display` / `lin_rec709_display`, sorting hint `cameraDistance`; compression to be done by extensions on top. Known implementations: CesiumJS, Cesium Native, JSplat, 3dgs_ply2gltf. — [KHR_gaussian_splatting README](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_gaussian_splatting/README.md)
- Ratification date 2026-09-03 via a registry commit, with no Khronos announcement; the most advanced compression extension is the draft `KHR_gaussian_splatting_compression_spz_2`; Babylon.js and PlayCanvas shipped support. Release candidate was announced 3 Feb 2026; a Qualcomm L-GSC-based alternative for compression was also mentioned in Feb 2026. — [radiancefields Khronos page](https://radiancefields.com/platforms/the-khronos-group); [Godot GS issue citing 2026-09-03](https://github.com/klausi3D/godotGS/issues/1190); [CG Channel, Feb 2026](https://www.cgchannel.com/2026/02/3d-gaussian-splats-are-being-added-to-the-gltf-standard/); [Khronos RC press release](https://www.khronos.org/news/press/gltf-gaussian-splatting-press-release). Conflict: pages updated in July 2026 still say "Release Candidate"; the registry README now says ratified.
- Cesium shipped KHR_gaussian_splatting in CesiumJS and Cesium for Unreal in March 2026. — [radiancefields, Cesium](https://radiancefields.com/cesium-brings-khr_gaussian_splatting-support-to-cesiumjs-and-unreal-engine)
- OpenUSD v26.03 (late March 2026): `UsdVolParticleField` schema family incl. `UsdVolParticleField3DGaussianSplat`, from the AOUSD Emerging Geometry Interest Group; reference Hydra renderer `hdParticleField` and a PLY -> USD script `py3dgsPlyToUsd.py` in `extras/imaging/examples/hdParticleField/`; core libraries on PyPI. — [AOUSD v26.03](https://aousd.org/blog/openusd-v26-03/); [radiancefields OpenUSD 26.03](https://radiancefields.com/openusd-26.03-adds-native-gaussian-splat-support); [Omniverse Particle Fields](https://docs.omniverse.nvidia.com/materials-and-rendering/latest/particle-fields.html)
- 3DGRUT exporters: `python -m threedgrut.export.scripts.transcode model.ply -o model.usdz --format lightfield` (ParticleField) or `--format nurec`; options `--max-sh-degree`, `--half`, `--half-geometry`, `--half-features`; `.usdz` layers must stay < 4 GiB (`--max-particles-per-field`, `--separate-partition-files`). — [3DGRUT export README](https://github.com/nv-tlabs/3dgrut/blob/main/threedgrut/export/README.md)
- gsplat 1.5.1 can write `.ply`, `.splat` and `.ply_compressed` itself via `export_splats`. — [gsplat releases](https://github.com/nerfstudio-project/gsplat/releases)

### Inferences
- Bytes per Gaussian, derived: standard PLY with SH3 = 59 floats (236 B; 248 B with the unused normals), so 76 % of a PLY is f_rest; PLY with SH0 = 14 floats (56 B); antimatter15 `.splat` = 32 B (no SH); compressed PLY ~16 B + chunk headers (SH optional) (from prior knowledge of the SuperSplat layout, not re-verified here); SPZ v4 ~20 B raw before ZSTD (no SH); SOG ~17-19 B raw before WebP. For our ~150-300k-Gaussian object scans that is roughly: PLY SH3 35-75 MB, `.splat` 5-10 MB, SPZ/SOG with SH0 a few MB. These are estimates; measure (section 6).
- Since our `.splat` already discards SH, SOG or SPZ written with `-H 0` (or `-H 1` if view-dependence is worth it) would be a direct 2-5x smaller replacement at equal visual content, at the cost of an extra decode step in the viewer (WebP decode for SOG, ZSTD for SPZ v4).
- KHR_gaussian_splatting GLB is a lossless interchange format (PLY-sized); not a size win until the SPZ compression extension is final. Useful only if we want a glTF pipeline (Cesium, Babylon, three.js).
- For Isaac Sim, the target container is now OpenUSD ParticleField (`--format lightfield`); NuRec USDZ is the legacy path (section 4).
- Antialiased training (`rasterize_mode="antialiased"`) changes how opacity must be interpreted; SOG has a `model: "antialiased"` flag but `.splat`/SPZ do not, so if we switch training mode the viewer and converters must match.

### Gaps
- `.ksplat` (mkkellogg) and SuperSplat compressed-PLY byte layouts were not re-verified from primary sources in this pass.
- No measured SOG vs SPZ decode/load times for small (<1M) splats found.
- Whether the July 2026 KHR SPZ compression draft (`..._spz_2`) is implemented by any viewer we would use is unknown.

## 3. Web rendering: fastest browser renderers in 2026, sorting strategies, and what to do with our WebGL2 viewer

### Takeaway
The 2026 landscape split into WebGL2 renderers with a worker-side CPU sort (Spark 2.x by World Labs, three.js-based, MIT, LoD streaming, Rust/WASM decoders) and WebGPU renderers with a per-frame GPU radix sort (PlayCanvas SuperSplat 3.0 rewrote its editor on WebGPU in Sept 2026; three.js r186 ships a native TSL `GaussianSplat`; WebSplatter paper). For our small object scans on an RTX 2070 Super our own viewer's design is adequate; the two cheap fixes are moving the sort off the main thread and halving the texture size, and the cheapest "adopt a library" option is Spark (reads ply, spz, splat, ksplat, sog) if we accept a three.js dependency.

### Cited Findings
- Spark (sparkjs.dev, "Built by World Labs", three.js renderer): format list "ply, sogs, spz, splat, ksplat"; programmable splat effects; mixing meshes and splats. — [sparkjs.dev](https://sparkjs.dev/)
- Spark 2.0: developer preview reported 21 Feb 2026 (MIT, three.js), full release with LoD/streaming in April 2026 (World Labs post dated 14 Apr 2026); targets WebGL2 deliberately ("almost guaranteed to run on every device"); computes splat distances on the GPU, reads them back and runs a two-pass radix sort in a Web Worker; LoD traversal in Rust -> WASM; splat budgets 500K (phone) to 2.5M (desktop), 16M-splat GPU page pool in 64K pages. — [World Labs, Spark 2.0](https://www.worldlabs.ai/blog/spark-2.0); [CGWorld, preview](https://cgworld.jp/flashnews/01-202603-Spark2.html); [radiancefields, Spark 2.0](https://radiancefields.com/world-labs-releases-spark-v2.0)
- Spark v2.2.0 (first tag in ~4 months after 2.0, coverage dated Sep 2026): all JS decoders replaced by Rust/WASM decoders, sort up to ~20 % faster, `WEBGL_provoking_vertex` first-vertex mode up to 14 % more FPS on some systems, opt-in faster LoD traversal, three.js r183-r186 compatibility fixes, NaN/black-splat fix for negative colours. — [radiancefields, Spark v2.2.0](https://radiancefields.com/spark-v2.2.0-adds-faster-lod-traversal-rust-decoders)
- SuperSplat 3.0 (v3.0.0, 18 Sep 2026, PlayCanvas Engine 2.22.0, splat-transform 3.3.3): editor rewritten around WebGPU; projection, culling, compaction and depth sort on the GPU every frame (compute projector -> GPU radix sort -> indirect draw); WebGL2 path and CPU sort worker removed; "Stochastic Alpha" mode skips the full sort while moving; requires current Chrome/Edge, Safari 26+, or Firefox with WebGPU; imports PLY, compressed PLY, SPLAT, KSPLAT, SPZ, LCC, SOG, streamed SOG; exports PLY, compressed PLY, SOG, SPZ, HTML/ZIP viewers (SOG export needs WebGPU). Whether the engine's runtime (not the editor) sorts on the GPU is not stated. — [Digital Production, SuperSplat 3](https://digitalproduction.com/2026/09/18/supersplat-3-moves-editing-to-webgpu/)
- three.js r186 merged a native Gaussian splat renderer (class reported as `GaussianSplat`, earlier `GaussianSplatMesh`) written in TSL, with loaders for ply, spz, splat, ksplat and glTF KHR_gaussian_splatting, splat raycasting and per-mesh frustum culling; sources conflict on whether it works only with `WebGPURenderer` or also its WebGL fallback; no LoD or chunked streaming in the first version. — [radiancefields, r186 ships](https://radiancefields.com/three.js-ships-its-native-gaussian-splat-renderer-and-splat-raycasting-in-r186); [radiancefields, r186 merge](https://radiancefields.com/three.js-merges-a-native-gaussian-splat-renderer-for-webgpu-in-r186); [oflight guide](https://www.oflight.co.jp/en/columns/threejs-r186-native-gaussian-splatting-guide-2026)
- mkkellogg GaussianSplats3D: last push reported 19 Oct 2025 with 82 open issues (possibly stale listing); no official deprecation notice found. — [gittrend listing](https://gittrend.io/repo/mkkellogg/GaussianSplats3D)
- WebSplatter (arXiv 2602.03207, Feb 2026): WebGPU pipeline with a wait-free hierarchical radix sort (WebGPU lacks global atomics), 1.2x-4.5x faster than state-of-the-art web viewers; a paper, not a library. — [arXiv 2602.03207](https://arxiv.org/abs/2602.03207v1)
- Avala's commercial viewer: GPU radix sort every frame on WebGPU, no WebGL fallback, Chrome/Edge 113+ best supported. — [Avala docs](https://docs.avala.ai/visualization/rendering/webgpu-acceleration)

### Inferences
- Our `cloud.js` is structurally the antimatter15 design, minus its two cheap optimisations: (1) the sort and the PLY/.splat parsing run in a Web Worker (ours block the main thread on every view change: ~3 passes over N plus a 64K histogram, fine at 150k, janky at >1M); (2) the texture packs a Gaussian in 2 RGBA32UI texels (position as float32, covariance as 6 halfs, colour as 4 bytes = 32 B) instead of our 4 RGBA32F texels (64 B), halving texture memory and vertex-shader fetches. Both keep the `.splat` file format unchanged.
- Other low-cost wins: precompute covariance in the worker (already done once at load, good); only re-sort when the view direction changes by more than a small angle, not any change of the 5-decimal view key; frustum-cull in the sort pass so off-screen Gaussians do not enter the index buffer; enable `WEBGL_provoking_vertex` like Spark 2.2 if we move to flat varyings.
- Adopt a library only if we need SH, LoD/streaming of multi-million-Gaussian room scans, or compressed formats: Spark 2.2 (WebGL2, works everywhere, reads all our candidate formats incl. SOG and SPZ) is the closest drop-in and keeps WebGL2; the PlayCanvas engine is the natural reader for SOG; three.js r186's native splat is WebGPU-first and young. The RTX 2070 Super supports WebGPU in Chrome on Windows, so a WebGPU path is possible for the laptop but is not needed for 100-300k splats.
- Keep `.splat` as the default only while files stay small; switch to SOG/SPZ when room-scale scans (millions of Gaussians) reach the console, at which point a library decoder is less work than writing a WebP/ZSTD decoder ourselves.

### Gaps
- No independent, same-machine fps benchmark of Spark vs PlayCanvas vs three.js r186 vs a hand-written WebGL2 viewer found; Spark's post gives budgets, not fps.
- three.js r186's WebGL support for `GaussianSplat` is contradictory in the sources; the official release notes were not read.
- Spark's exact npm package name and current version number were not verified in this pass.

## 4. Native / Isaac Sim rendering: bringing a trained splat into Isaac Sim 5.0 / 6.0, performance, physics proxies

### Takeaway
Isaac Sim 6.0 (GA 4 Jun 2026, Kit 110) renders splats natively in RTX as OpenUSD ParticleField prims and still reads the older NuRec USDZ; Isaac Sim 5.0-6.0 (Kit 107.3-110.1) read NuRec USDZ. The conversion from our standard PLY is one 3DGRUT command (`transcode ... --format lightfield` for ParticleField, `--format nurec` for legacy NuRec). Collision is not provided by the splat: a separate invisible mesh (from our RGB-D fusion, or splat-transform's voxel/collision-mesh output) must carry physics.

### Cited Findings
- 3DGRUT export README: NuRec USDZ supported in Omniverse Kit 107.3 to 110.1 and Isaac Sim 5.0 to 6.0; Isaac Sim 6.0 supports the ParticleField (standard USD) schema; NuRec "is going to be deprecated and replaced by `ParticleField`", ParticleField preferred for new assets; beta, workflows may change. Commands: `python -m threedgrut.export.scripts.transcode model.ply -o model.usdz --format lightfield|nurec`, `python -m threedgrut.export.scripts.ply_to_usd model.ply --output_file out.usdz`, or `export_usd.enabled=true` at the end of 3DGRUT training. — [3DGRUT export README](https://github.com/nv-tlabs/3dgrut/blob/main/threedgrut/export/README.md); [3DGRUT](https://github.com/nv-tlabs/3dgrut)

### Inferences
- Our path: `NAME.ply` (standard layout, which 3DGRUT's transcoder reads) -> `transcode --format lightfield --max-sh-degree 3 --half` -> reference from a `.usda` root stage in Isaac Sim 6.0. Keep `--format nurec` as a fallback for Isaac Sim 5.0 and for a quality A/B (forum report).
- Our world is z-up metres (scan frame); USD stages are usually z-up metres too, but check 3DGRUT's axis assumptions on PLY input (PLY from COLMAP-style training is usually y-down/RDF).
- Physics: build the collider from the RGB-D data we already have (TSDF/Poisson mesh from the scan, or a convex hull/box of the object's points) as an invisible `UsdGeom.Mesh` with `UsdPhysics.CollisionAPI` placed in the same frame; the splat is only the visual. splat-transform's voxel/collision-mesh output is an alternative for room scans.
- Rendering cost: 3DGRUT's own 5090 numbers (3DGUT 317 FPS at MipNeRF360 scale, 3DGRT 68 FPS) suggest an object splat is cheap; the RTX path-traced ParticleField cost inside Isaac Sim was not quantified anywhere. The sRGB/no-tonemap handling and the black-render threads match the "black-render trap" already noted for our M3 sim work, so test on the exact Isaac Sim build used on hekate/Dionysos.
- Isaac Sim 5.0 (Kit 107.3) supports only the NuRec path; ParticleField needs 6.0+.

### Gaps
- No official Isaac Sim numbers for ParticleField render FPS or VRAM per million Gaussians.
- Whether NuRec/ParticleField contribute to Isaac Sim depth sensors and RTX lidar (beyond "accumulated depth" settings) is not documented on the pages read.
- No NVIDIA guidance on collision proxies for splat assets found.
- The exact OpenUSD/ParticleField schema version Isaac Sim 6.0 vs 6.1 expects (and whether `py3dgsPlyToUsd.py` output loads in 6.0) not confirmed.

## 5. Splats on the Jetson Orin (rendering or training on the robot)

### Takeaway
Stock 3DGS rendering on Orin-class Jetsons is not real-time for scene-scale splats; published work reports single-digit to low-double-digit FPS on Orin NX and needs algorithmic or hardware changes to reach 90 FPS on AGX Orin. For small object splats at low resolution it may be usable, but no measured numbers for gsplat on an Orin NX at our sizes were found; training on the robot is not worth pursuing given a 5090 is a LAN hop away.

### Cited Findings
- LS-Gaussian (arXiv 2507.21572v2, 30 Jul 2025): 3DGS "still struggles to achieve real-time rendering at 90 FPS" on edge platforms such as Jetson AGX Orin; rasterization (not sorting) dominates render time; LS-Gaussian is 5.41x faster than the AGX Orin GPU baseline in software, 17.3x with a custom accelerator. — [arXiv 2507.21572](https://arxiv.org/html/2507.21572v2)
- Other on-device works surfaced by search: Voyager (city-scale splats on resource-constrained devices), Neo (reuse-and-update sorting, simulator results vs AGX Orin baseline), Gaussian Blending Unit (edge GPU plug-in for AR/VR). — [Voyager](https://arxiv.org/pdf/2506.02774); [Gaussian Blending Unit](https://arxiv.org/html/2503.23625v1)
- Brush builds for Android arm64 and runs on WebGPU-capable GPUs (a possible path to on-device training without CUDA). — [Brush](https://github.com/ArthurBrussee/brush)

### Inferences
- For the robot, a splat is more useful as a rendered reference (e.g., render-and-compare for pose or "what the object should look like" checks) than as a live display; at 640x480 and ~100-300k Gaussians gsplat's CUDA rasterizer on the Orin NX (Ampere, 1024 CUDA cores) may reach usable rates, but it competes with the vision services (TensorRT detectors, depth model) for the GPU.
- Training on the Orin NX (16 GB shared memory) is feasible only for tiny fits; the existing hekate round trip (~1 min) is the better design.

### Gaps
- Search snippets attributed 2-9 FPS, 4.9-8.5 FPS and 7-17 FPS for stock 3DGS on Orin NX to specific papers, but those figures were not confirmed in the papers themselves (the LS-Gaussian text does not mention Orin NX); treat as unverified.
- No gsplat-on-JetPack build/benchmark reports found.

## Benchmark plan for splats

All GPU runs go on hekate (RTX 5090) per CLAUDE.md: check `tools/status.ps1` first, ask before anything GPU-heavy when < ~16 GB VRAM is free, never touch Isaac Sim or jobs we did not start. Use one fixed scan (e.g. the newest `m3pro/out/scan/<STAMP>`) plus one second object (a box) so results are not tuned to one can; 3 seeds per variant.

### What to measure
1. Training: wall time to a target held-out PSNR (log held-out PSNR every 500 steps, report the step and time when it first reaches the final-7000-step value minus 0.2 dB), final held-out PSNR after alignment (the number `train_splat.py` prints), median depth error (mm) on held-out views, Gaussian count, peak VRAM (`torch.cuda.max_memory_allocated`), it/s.
2. Format: file bytes, encode time, decode-back fidelity (held-out PSNR re-rendered from the decoded file minus PSNR from the original PLY), per format and SH degree.
3. Browser (laptop, RTX 2070 Super, Chrome): time from `fetch` start to first drawn frame, steady-state frame time while orbiting (median and 95th percentile over 10 s), main-thread sort time per re-sort, JS heap and GPU texture bytes.
4. Isaac Sim (later, only with the user's go-ahead, Isaac Sim is shared): load time, render FPS of one camera at 640x480, RGB PSNR and depth error vs real held-out frames, for ParticleField vs NuRec USDZ.

### Variants and commands
- Baseline (now): `splat\splat.bat SPLAT_DIR --steps 7000 --name base` (prints held-out PSNR, depth mm, count, seconds).
- Training variants (flags to add to `train_splat.py`, each a few lines): `--steps 3000|5000|7000`; `--sh 0|1|3` (max SH degree); `--ssim fused` (pip `fused-ssim`, as gsplat's simple_trainer); `--adam selective` (gsplat `SelectiveAdam`); `--packed`; `--strategy default|default-absgrad|mcmc --cap 150000|300000` (`DefaultStrategy(absgrad=True, grow_grad2d=0.0008)` with `rasterization(..., absgrad=True)`, or `MCMCStrategy(cap_max=...)`); `--log-every 500` to log held-out PSNR during training. Then a separate venv with gsplat main (PyTorch >= 2.7, CUDA 12.8) for the same baseline, to see what the 2026 kernels give.
- Other trainers on the same scan (export as nerfstudio `transforms.json` with poses already in it): 3DGRUT 3DGUT (`python train.py --config-name apps/<nerf-style 3dgut config> path=SPLAT_DIR ... export_usd.enabled=true`), Brush (`brush SPLAT_DIR --with-viewer` style CLI; no depth supervision, so compare PSNR only).
- Formats from one `NAME.ply` (laptop is fine, CPU or `-g cpu`): `splat-transform NAME.ply NAME.sog`, `splat-transform NAME.ply -H 0 NAME_sh0.sog`, `splat-transform NAME.ply NAME.spz` (`--spz-version 4`), `splat-transform NAME.ply -H 0 NAME_sh0.spz`, `splat-transform NAME.ply NAME.compressed.ply`, `splat-transform NAME.ply NAME.glb`, `splat-transform NAME.ply --stats null`; plus our `NAME.splat` and gsplat's `export_splats(..., format="ply_compressed")`. Decode back with `splat-transform NAME.sog NAME_from_sog.ply` and score with a small `eval_splat.py` that reads a PLY (`read_ply`), renders the held-out views at the poses in `NAME_poses.json` (aligned c2w is already saved there) and prints PSNR/depth error.
- Browser: one static test page per renderer, all loading the same scan: our `cloud.js` (`.splat`), Spark 2.2 (`.splat`, `.spz`, `.sog`, `.ply`), the PlayCanvas engine (`.sog`, `.compressed.ply`), and three.js r186 `GaussianSplat` with `WebGPURenderer` (`.ply`, `.spz`). Each logs `performance.now()` at fetch start, after decode, and at the first `requestAnimationFrame` after upload, then runs a scripted 10 s orbit at 1920x1080 and records frame deltas. Launch Chrome with `--disable-gpu-vsync --disable-frame-rate-limit` so frame times are not capped at the display rate; DevTools "Disable cache" for cold loads, and repeat warm. For our viewer, A/B the worker sort and the 32-byte RGBA32UI packing against the current main-thread sort and 64-byte RGBA32F texture.
- Isaac Sim A/B (with permission): `python -m threedgrut.export.scripts.transcode NAME.ply -o NAME_pf.usdz --format lightfield --half` and `... -o NAME_nurec.usdz --format nurec`, referenced from a `.usda` root stage, launched with the 6.x flags `--/rtx/spg/enabled=true --enable omni.rtx.spg`.

### Pitfalls
- Coordinate conventions differ: our scan frame is z-up metres; SPZ defaults to RUB, PLY from training pipelines is usually RDF, glTF is y-up (LUF in SPZ's terms), SOG is right-handed y-up. Check orientation visually after every conversion; a mirrored axis flips rotation handedness silently.
- Activation conventions: PLY stores logit opacity, log scales and SH coefficients (f_rest channel-major); `.splat` stores linear opacity/scale and RGB = 0.5 + C0 * f_dc. Converters differ in clamping; compare decoded PLYs, not files.
- `rasterize_mode="antialiased"` (Mip-Splatting style) changes opacity semantics; only SOG carries an "antialiased" flag. Keep classic mode unless the viewer applies the same compensation.
- Colour space: KHR_gaussian_splatting declares sRGB or linear; Omniverse treats ParticleField as display-referred sRGB and skips tonemapping; our trainer fits sRGB camera images. Do not apply a second gamma.
- SOG must use lossless WebP; lossy encoding corrupts the codebook indices.
- Held-out PSNR must be computed after pose alignment (as `train_splat.py` does); unaligned numbers mix pose error into format comparisons.
- Training-time comparisons: exclude the first-run CUDA JIT build (gsplat compiles kernels on first use; on Windows our MSVC build), and the image loading; time only the step loop. Pin the scan, the seed and the GPU clock state; another job on hekate's GPU changes results, so record `nvidia-smi` utilisation at start.
- Browser numbers: a 60 Hz cap, background-tab throttling, and first-frame shader compilation all distort results; report median frame time, not "fps", and separate cold and warm loads.
- Gaussian counts differ between variants (MCMC cap vs densification); compare file sizes at equal PSNR, not at equal settings.
